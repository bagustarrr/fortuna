> Полный контекст и история решений. Рабочая выжимка, которая подхватывается

## 1. Что это за проект

Интерактивная **диагностика познавательных способностей ребёнка** для школы
программирования KURSOR (Астана, 1000+ учеников, резидент Astana Hub).

**Бизнес-задача:** поднять доходимость на мастер-класс. Сейчас записывается ~20,
приходит ~8 (40%). Цель — 60–70%.

**Как работает механика:**
1. Лидоруб (менеджер) созвонился с родителем, записал на мастер-класс.
2. Родителю уходит ссылка на диагностику.
3. Ребёнок дома проходит тест (8–12 минут) — мини-игры + вопросы.
4. Родитель видит **часть** результата: 3 сильные стороны + закрытый профиль.
5. Полную расшифровку даёт специалист лично на мастер-классе.
6. → у родителя появляется личная причина прийти («узнать про своего ребёнка»),
   которую нельзя отложить и нельзя получить онлайн.

## 2. Ключевой принцип — ЧЕСТНОСТЬ результата (не нарушать!)

Результаты **настоящие, но раскрыты частично**. НЕ выдуманные.

- Ребёнок реально проходит задания, система реально считает профиль по поведению.
- Родитель видит реальные сильные стороны — но без интерпретации (что значит, что делать).
- Интерпретацию даёт специалист очно.

**Почему нельзя выдумывать:** родители в Астане общаются, дети сравнивают экраны.
Два ребёнка с разными ответами и одинаковым результатом = репутация «гадалки» + отзывы.
Тот же класс риска, что и выдуманные госпрограммы (это красная линия проекта).

Профиль из шкал устроен так, что у ЛЮБОГО ребёнка что-то будет наверху
(математически неизбежно). Плохого результата не получает никто — и никто не соврал.

**Слабые стороны — только устно у специалиста. Письменно НЕ отдаём никогда.**

## 3. Возрастные группы (ФИНАЛЬНО, без пересечений)

| Группа   | Возраст | Особенности |
|----------|---------|-------------|
| Младшая  | 6–8     | Умеют читать (1 класс+), но проще: крупнее, меньше абстракции, ~6–8 мин |
| Средняя  | 9–11    | Текущая базовая версия. Циклы есть, условий мало |
| Старшая  | 12–17   | Максимальная сложность: циклы + условия, поиск ошибки, полные термины |

**Сделано.** Три версии разведены: конфиг `AGES` в `diagnostika_kursor.jsx`
(`junior` / `middle` / `senior`), выбор по возрасту — `ageKeyFor(age)`.
Различаются: набор и сложность заданий, длина последовательностей в памяти,
уровни робота, тексты инструкций, размер шрифта и клеток.

**Цвет тоже разный** — `PALETTES`: младшая светло-зелёная, средняя оранжевая,
старшая остаётся исходной бирюзовой. Так родителю и заказчику сразу видно, что
версии разные. Палитра выставляется один раз при старте (`applyPalette`), фон до
загрузки скрипта красит инлайн-скрипт в `scripts/template.html`.

Оговорка: цвета фигур в «Закономерностях» (`shapes` в палитре) — функциональные.
На них построено правило «чередование цвета», поэтому их нельзя брать из акцентов
интерфейса: в оранжевой теме два акцента слились бы и задание перестало бы
решаться. Попарный контраст проверяет `npm run validate`.

Проверить версии: `#age=7`, `#age=10`, `#age=15` (читается и `?age=`, и `#age=` —
при открытии с диска и на части хостингов query-строка теряется, хэш доходит
всегда). Если параметры заданы, на интро видна плашка с номером версии; по боевой
ссылке из amoCRM параметров нет, и плашки нет.

## 4. Состав теста (текущая реализация)

Файл `diagnostika_kursor.jsx` — один React-компонент (default export `App`).
Поток экранов строится из `AGES[key].flow`: перед каждой мини-игрой идёт
экран-инструкция с живым примером.
`intro → (инструкция + игра) ×3 → q1 → (инструкция + игра) ×3 → q2 → self → result`

**Блок 1 «Как ты думаешь»** — три мини-игры:
- *Закономерности* (`Patterns`) — ряд фигур с пропуском. Задания генерируются
  (`buildPatterns`) из правил `RULES`, сложность растёт по `PATTERN_PLANS[возраст]`.
  Для старшей группы добавлены правила с двумя независимыми циклами разной длины.
- *Память* (`Memory`) — клетки вспыхивают по очереди, ребёнок повторяет порядок.
  Длина последовательности растёт. Даёт РП-04.
- *Пространство* (`Spatial`) — посчитать кубики в изометрической постройке
  (включая невидимые опоры) и найти ту же фигуру после поворота, где зеркальная
  копия — ловушка. Даёт МРТ-03.

**Блок 2 «Алгоритмы»** — три мини-игры:
- *Робот* (`Robot`) — ведёт робота к цели командами Вперёд/Налево/Направо.
  На дальних уровнях команд заведомо не хватает и работает **множитель**
  («Вперёд ×5») — скрытая проверка на понимание ЦИКЛА. Пулы уровней —
  `ROBOT_POOLS[возраст]`, один выбирается случайно.
- *Поиск ошибки* (`Debug`) — программа написана целиком, робот до цели не доходит.
  Ребёнок смотрит трассировку и указывает неверную команду. Даёт ВРФ-05.
- *Порядок шагов* (`Order`) — расставить шаги алгоритма по порядку. У старшей
  группы в шагах есть условие и повторение.

Все уровни робота и все задачи «поиска ошибки» проверяются перебором
(`npm run validate`): уровень проходим за отведённое число команд, уровень с
множителем без множителя НЕ решается, а в задаче на ошибку ровно одна команда
поддаётся починке.

**Вопросы** (`Q1_POOLS`, `Q2_POOLS`) — свои формулировки на каждый возраст,
измеряют стиль мышления (планирование, реакция на ошибку). Разный текст, одно
измеряемое значение.

**Самооценка** — «сколько решил правильно» → сравнивается с реальностью
(метакогнитивная рефлексия).

**Экраны-инструкции** (`HowTo` + `EXAMPLES`) — перед каждой мини-игрой правила
показываются на живом примере. Без них дети не понимают задание.

## 5. Что измеряем — шкалы (14 параметров)

Измеряются 11, закрыты до разбора 3 (`LOCKED`: УПВ-07, ЛКО-12, ПКН-14).

**Из правильности ответов:** декомпозиция/алгоритмизация (ДКМ-01), индуктивный
вывод (ИНД-02), мысленное вращение (МРТ-03), рабочая память (РП-04),
верификация и поиск ошибок (ВРФ-05).

**Из ПОВЕДЕНИЯ** (это и делает продукт диагностикой, а не тестом):
- Толерантность к фрустрации (ТФР-06) — сколько раз пробует после неудачи
- Реакция на нарастающую нагрузку (АНН-10)
- Когнитивная беглость (КБГ-08) — скорость **верных** решений: без поправки
  на точность её получал бы ребёнок, который просто быстро щёлкает наугад
- Баланс скорости и точности (БСТ-09)

**Из вопросов:** стратегия планирования (СТП-11), метакогнитивная рефлексия (МКР-13).

Термины настоящие (когнитивная психология) — звучат солидно и специалист их
защитит на разборе. НЕ измеряем: трудолюбие, доброту, ответственность
(кликами не меряется, пришлось бы врать).

Расчёт — функция `compute(data, n)`. Нормировка 0–100 внутри профиля одного ребёнка,
с мягким сжатием у верхнего края (чтобы сильные не слипались в 97).

## 6. Экран результата

**Показываем:** шапка-заключение (имя, возраст, дата), 3 сильные стороны с кодами
и шкалами, блок «Что зафиксировала система» (реальные наблюдения из данных),
рекомендованное направление (ЗАКРЫТО под замок), блок «Разбор на встрече».

**Прячем (под blur + замок):** остальные параметры, расшифровку, направление,
рекомендации. Крючок: «полный разбор — на встрече со специалистом».

**Склонение имени:** есть функция `declineName()` — падежи + род (учитывает
казахские женские имена на согласный, которые не склоняются: Айгерим, Айгуль).
`yearsWord()` — «лет/года/год». Наблюдения согласованы по роду (сам/сама).

## 8. Технический стек и деплой

- **Фронт:** React + Vite. Только Tailwind-совместимые inline-стили, без внешних CSS.
- **Сборка HTML:** `index.html` — самодостаточный файл (React + код вшиты внутрь),
  собирается через esbuild. Работает на Netlify перетаскиванием.
- **Конфиги:** `netlify.toml`, `_redirects` — для SPA-роутинга (ссылки вида `/t/токен`)
  и `noindex` (прототип не в поиске).
- Проверка вёрстки — прогон через jsdom (эмуляция браузера), кликами весь путь.

**Команды** (один раз `npm i`):
```
npm run validate   # перебором проверяет уровни робота и задачи «поиск ошибки»
npm run smoke      # проходит тест кликами в jsdom: 3 возраста × 2 стиля игры
npm run build      # пересобирает index.html из jsx и проверяет, что он запускается
npm run check      # всё сразу
```
`scripts/template.html` — шаблон страницы, бандл подставляется вместо `/*BUNDLE*/`.
**После любой правки jsx обязательно `npm run build`**, иначе задеплоенный
`index.html` разъедется с исходником.

Прогон `smoke` не «жмёт что попало»: он читает поле робота из DOM, сам ищет путь
до цели, ловит вспышки в игре на память и вычисляет неверную команду. Один стиль
игры — «умный» (проверяет ветки успеха в `compute`), другой — «ленивый»
(проверяет ветки неудачи).

## 9. BACKEND и amoCRM — следующий большой этап (ещё НЕ сделан)

Выбран **полный вариант с автоматизацией**. Схема:

```
amoCRM  ──webhook──▶  наш сервер  ──▶  Supabase (база)  ◀──▶  фронт-тест
```

**Сценарий:**
1. Лидоруб в карточке amo указывает имя ребёнка + возраст, ставит этап
   «Назначен на мастер-класс».
2. amo дёргает webhook → сервер создаёт **разовую ссылку** с данными из карточки
   (имя, возраст → выбор возрастной версии, дата/время встречи).
3. Ссылка возвращается в поле карточки amo → лидоруб отправляет родителю.
4. Ребёнок проходит → результат **падает обратно в amo** (статус, сильная сторона,
   ссылка на отчёт).

**Разовость ссылки (решено):**
- Сгорает **после ЗАВЕРШЕНИЯ** теста (после показа результата), НЕ после открытия.
- Если бросил на середине — можно продолжить (автосохранение уже есть в коде).
- Повторное открытие использованной ссылки → экран
  «Тест уже пройден, результаты у вас на встрече».

**Стек backend:** Supabase (Postgres + API + функции), free tier.
Хранит: токен ссылки, имя, возраст, дату встречи, статус, ответы, тайминги,
поведенческие метрики, результат, все события.

**Статусы теста для amo:** не открыт → начат → пройден.
Лидоруб фильтрует «не открыт» за 2 дня до встречи → обзвон спящих
(это само по себе поднимает доходимость).

**amo настраивает сотрудник заказчика.** Нужно дать ему пошаговую инструкцию:
какие кастомные поля создать, как называется этап-триггер, как настроить webhook.

## 12. Ограничения и правила (важно соблюдать)

- Никаких выдуманных данных в результате (см. раздел 2).
- Никаких психологических/медицинских ДИАГНОЗОВ. Дисклеймер уже есть в коде:
  «оценивает познавательные процессы, не является психологическим/медицинским заключением».
- «Специалист» на встрече — НЕ психолог/диагност, если нет образования.
  Безопасно: методист, преподаватель, руководитель учебного отдела.
- Согласие родителя на обработку данных ребёнка — есть чекбокс на интро,
  но точную юридическую формулировку должен дать юрист заказчика.
- Никаких localStorage/sessionStorage в артефактах-версии (в боевой — Supabase).
